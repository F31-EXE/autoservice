# Decisions & assumptions

Лог решений, принятых по неоднозначным местам ТЗ. Формат: этап — решение — почему.

## Этап 1. Каркас

1. **Django 5.2 LTS** (ветка 5.x с долгой поддержкой).
2. **`apps/common`** — дополнительное приложение вне структуры ТЗ: `TimeStampedModel`,
   `TenantQuerySet`, PII-фильтр логов. Нужно, чтобы не было циклических зависимостей между apps.
3. **Изоляция арендаторов — явный `Model.objects.for_user(user)`** (метод `TenantQuerySet`).
   Каждый бизнес-QuerySet задаёт `station_path` до `ServiceStation`. Неявная фильтрация через
   thread-local не используется: она ломает Celery-задачи и админку и скрывает ошибки.
   `objects.all()` разрешён только в фоновых задачах и Django admin.
4. **Права по ролям:** Superadmin — всё; Owner — все точки своей организации;
   Manager — только точки из `User.stations` **и** только своей организации (пересечение,
   поэтому ошибочно выданная чужая точка в M2M не даёт доступа).
5. **Django admin доступен только Superadmin**: `is_staff` выставляется автоматически из роли
   в `User.save()`. `is_superuser` считается Superadmin.
6. **Текущая точка** кабинета хранится в сессии; переключатель в шапке, если точек > 1.
7. **Настройки СТО** (`ServiceStation.settings`) читаются через `station.conf` — слияние с
   дефолтами из раздела 7.3; неизвестные ключи игнорируются. Ключ `llm_compose_enabled` (8.3)
   тоже живёт здесь.
8. **Логи:** корневой handler пропущен через `PiiScrubFilter` (маскирует телефоны, e-mail, VIN,
   госномера) — страховка; основное правило — не логировать ПДн вообще.
9. **Celery beat** — `django-celery-beat` (DatabaseScheduler), расписания будут создаваться
   миграциями/командами на этапе 5. Время в Celery — UTC, локальное время СТО считается в коде.
10. **CSS/JS:** Pico.css 2.0.6 + HTMX 2.0.4 лежат в `static/vendor/` (не CDN: зарубежные CDN
    из РФ доступны нестабильно, кабинет не должен от них зависеть). Статику в проде отдаёт
    WhiteNoise.
11. **Тесты** гоняются на PostgreSQL (как в проде), `config.settings.test`: Celery eager,
    in-memory storage, ключи внешних API принудительно пустые.
12. **Локально Python 3.13**, в Docker — 3.12 (как в ТЗ); код совместим с обоими.

## Правки схемы данных (согласованы после этапа 1)

Вносятся в соответствующих этапах, когда появляются модели:

1. `Recommendation.planned_for` (date, nullable) — нужен для 7.4 («рекомендации с
   `planned_for <= today + 1`»); пересчитывается после импорта и изменений машины. *(этап 5)*
2. `Outreach.first_touch_at` (datetime, nullable) — начало окна атрибуции 9.1. *(этап 5)*
3. `Message.touch_number` (int) + `UniqueConstraint(outreach, touch_number)` для исходящих —
   защита от двойной отправки (раздел 11). *(этап 6)*
4. Лимит SMS: 2 склеенных сегмента UCS-2 = **134** кириллических символа (2 × 67), а не 140.
   Длину считаем по реальной кодировке: если текст целиком в GSM-7 — 2 × 153. *(этап 6)*
5. Уникальность клиента — условные ограничения PostgreSQL *(сделано на этапе 2)*:
   `(station, phone) WHERE phone IS NOT NULL` и
   `(station, external_id) WHERE phone IS NULL AND external_id IS NOT NULL`;
   плюс CHECK: должен быть телефон или внешний ID.

## Этап 2. Импорт

1. **Даты визитов — `DateField`** (`opened_at`, `closed_at`, `last_visit_at`): в выгрузках СТО
   время визита неинформативно, а планировщик работает в днях. Если колонка «дата закрытия» не
   задана и ЗН закрыт — `closed_at = opened_at`. У отменённых ЗН `closed_at` пуст.
2. **`ImportMappingProfile.layout`** (`flat|header`) — добавлено поле, в ТЗ формат описан, но не
   хранился. Также добавлены `ImportBatch.original_filename`, `finished_at`.
3. **Дополнительные логические поля маппинга** сверх ТЗ: «Отказы клиента» (ячейка со списком
   невыполненных работ — типично для формата «шапка ЗН»), «Сумма ЗН», «Статус ЗН», «Тип
   позиции», «Кол-во», «Цена», «Дата закрытия». Все необязательные.
4. **Идемпотентность**: ЗН ищется по `(station, external_number)`; для каждого ЗН считается
   `content_hash` нормализованных данных. Совпал — ЗН не трогаем («без изменений»), иначе
   обновляем поля, **полностью заменяем строки** и ставим `extraction_status=pending`.
   Вся запись выполняется в одной транзакции: падение воркера откатывает всё, задачу можно
   перезапустить. Задача повторно не обрабатывает уже завершённую загрузку.
5. **Сопоставление клиента**: сначала по телефону, затем по внешнему ID — но только если у
   найденного клиента нет телефона (или у строки его нет). Разные телефоны с одним внешним ID
   → разные клиенты (по ТЗ уникальность по телефону). Непустые ФИО/телефон/ID из файла
   дополняют карточку; согласия и отписка импортом не меняются.
6. **Сопоставление машины** — в пределах клиента: по VIN → по госномеру → по марке+модели
   (если ровно одна такая) → единственная машина клиента (если в строке нет данных о машине).
   Иначе создаётся новая. Смена владельца (тот же VIN у другого клиента) пока не
   отслеживается — две записи Vehicle.
7. **Нормализация**: телефоны через `phonenumbers` (регион RU, 10-значные «9…» и «8…»
   приводятся к +7), невалидные — `None` + предупреждение. Госномер: верхний регистр, без
   пробелов, латинские буквы-двойники → кириллица. Невалидный VIN отбрасывается.
   Признак выполнения: по умолчанию «выполнено»; «нет/0/отказ/не выполнено/…» → отказ.
   Если сумма ЗН не задана — сумма выполненных строк.
8. **Ошибки** пишутся с номерами строк файла и без значений ячеек (без ПДн), максимум 500.
   ЗН без даты или без телефона/ID пропускается целиком; некорректные необязательные поля
   — предупреждение, поле игнорируется.
9. **CSV**: кодировка UTF-8 (с BOM) или Windows-1251, разделитель определяется автоматически
   (`;`, `,`, tab). **XLSX**: строка заголовков — первая строка с ≥ 2 непустыми ячейками
   (пропускаем «шапку» отчёта), выбор листа на экране сопоставления.
10. **Профиль переиспользуется автоматически**, если для СТО и системы-источника есть профиль и
    все его колонки есть в новом файле; иначе — экран сопоставления с подстановкой из прошлого
    профиля и автоугадыванием по синонимам заголовков. Чекбокс «Настроить заново».
11. **Хуки для следующих этапов** — сигнал `work_orders_imported(batch, changed_work_order_ids,
    vehicle_ids)`; к нему подключатся извлечение рекомендаций (3–4) и атрибуция (7).
12. `pandas` убран из зависимостей — хватает `openpyxl` и `csv`, образ меньше.
13. **Производительность**: 10 000 строк (≈2 900 ЗН) — ~9 с, повторный импорт того же файла
    — ~2 с (локальный PostgreSQL).

## Этап 3. Справочник и правила

1. **Справочник — 89 видов работ** (`apps/catalog/seed_data.py`), засевается миграцией
   `catalog/0002` и командой `python manage.py seed_catalog` (идемпотентно: обновляет виды
   работ и пересоздаёт только *глобальные* синонимы; синонимы СТО не трогает). Интервалы —
   типовые рыночные значения, это стартовые дефолты. Регламентных (`is_regular`) — 17:
   масло ДВС, ТО, фильтры, свечи, ГРМ, приводной ремень, ОЖ, тормозная жидкость, ГУР, масла
   трансмиссии, сезонная смена шин (6 мес.), кондиционер (12 мес.).
2. **Синтаксис синонимов** (`WorkTypeAlias.kind`): `keywords` (по умолчанию) — группы через
   пробел, все должны встретиться как подстроки; `|` — альтернативы; `-слово` — запрет;
   `_` — пробел внутри альтернативы. Порядок слов не важен («Колодки пер. — замена» =
   «Замена передних колодок»). `regex` — для сложных случаев. Основы пишутся с учётом беглых
   гласных («колод», а не «колодк» — иначе не найдётся «колодок»).
3. **Выбор при нескольких совпадениях**: сначала синонимы СТО, затем глобальные; среди них —
   выше `priority`, затем самое специфичное совпадение (сумма длин найденных слов). Так
   «Замена масла АКПП» уходит в `atf_auto`, а не в `engine_oil`.
4. **Одна строка ЗН = один вид работ** (FK по ТЗ). «Замена масла и фильтра» — один тип
   `engine_oil` (масляный фильтр включён в него). Строки с несколькими разными работами
   получат один тип — ограничение, вернёмся при необходимости.
5. **Правила работают только по строкам-работам** (`kind=labor`); запчасти сопоставляются со
   справочником, но рекомендаций не создают (запчасть могли купить без установки).
   Работы открытых/отменённых ЗН сопоставляются, но рекомендаций не дают.
6. **Отказ без вида работ** (не нашёлся в справочнике) → рекомендация `needs_review`,
   `confidence=0.5`, `work_type_raw` = название строки. Отказ от работы, которая в этом же
   визите выполнена, игнорируется.
7. **Порядок обработки** — по каждой машине хронологически. Выполненная работа закрывает
   активные рекомендации того же типа с визитом источника не позже текущего (`done`,
   `closed_by_work_order`). Регламентная работа после этого создаёт новую рекомендацию.
8. **Обратная загрузка истории** (старые ЗН после новых): если есть активная рекомендация
   того же типа из более позднего визита — старый визит её не перезаписывает; если работа
   уже выполнена в более позднем визите — новая рекомендация сразу `done`.
9. **Обновление вместо дубля** (6.1): обновляются источник, срок, цитата, оценка;
   статус `scheduled` сохраняется, `needs_review` → `open`. Отклонённая менеджером
   рекомендация (`rejected`) из того же ЗН заново не создаётся. Если ЗН отредактирован и
   строки-основания больше нет — неподтверждённая рекомендация удаляется.
10. **Оценка стоимости `est_price`**: для отказа — сумма строки из сметы; иначе — средняя
    сумма этой работы (только работа, без запчастей) по СТО за 12 месяцев. Это заниженная
    оценка; прайс СТО — позже.
11. **TTL (6.4)** считается от ожидаемого срока (min(дата, дата по пробегу)), а если срока
    нет — от визита: иначе рекомендация «ремень ГРМ через 4 года» протухла бы раньше срока.
    Истечение — после каждого импорта и ежедневной задачей Celery beat.
12. Метод `Recommendation.expected_date()` реализует формулу 7.2 (без `remind_before_days`);
    поле `planned_for` добавим на этапе 5.
13. `python manage.py catalog_coverage --station N` — топ несопоставленных названий строк
    (названия работ — не ПДн). Инструмент для настройки синонимов на реальных выгрузках.
14. **Производительность**: правила работают в памяти по машинам с пакетной записью.
    10 000 строк (2 874 ЗН, 5 502 рекомендации) — импорт + правила ≈ 26 с.
15. Пока нет UI для синонимов СТО — правятся в Django admin (суперадмин).
