# Decisions & assumptions

Лог решений, принятых по неоднозначным местам ТЗ. Формат: этап — решение — почему.

## Этап 1. Каркас

1. **Django 5.2 LTS** (ветка 5.x с долгой поддержкой).
2. **`apps/common`** — дополнительное приложение вне структуры ТЗ: `TimeStampedModel`,
   `TenantQuerySet`, PII-фильтр логов. Нужно, чтобы не было циклических зависимостей между apps.
3. **Изоляция арендаторов — явный `Model.objects.for_user(user)`** (метод `TenantQuerySet`).
   Каждый бизнес-QuerySet задаёт `station_path` до `ServiceStation`. Неявная фильтрация через
   thread-local не используется: она ломает Celery-задачи и админку и скрывает ошибки.
   `objects.all()` разрешён только в фоновых задачах и Django admin.
4. **Права по ролям:** Superadmin — всё; Owner — все точки своей организации;
   Manager — только точки из `User.stations` **и** только своей организации (пересечение,
   поэтому ошибочно выданная чужая точка в M2M не даёт доступа).
5. **Django admin доступен только Superadmin**: `is_staff` выставляется автоматически из роли
   в `User.save()`. `is_superuser` считается Superadmin.
6. **Текущая точка** кабинета хранится в сессии; переключатель в шапке, если точек > 1.
7. **Настройки СТО** (`ServiceStation.settings`) читаются через `station.conf` — слияние с
   дефолтами из раздела 7.3; неизвестные ключи игнорируются. Ключ `llm_compose_enabled` (8.3)
   тоже живёт здесь.
8. **Логи:** корневой handler пропущен через `PiiScrubFilter` (маскирует телефоны, e-mail, VIN,
   госномера) — страховка; основное правило — не логировать ПДн вообще.
9. **Celery beat** — `django-celery-beat` (DatabaseScheduler), расписания будут создаваться
   миграциями/командами на этапе 5. Время в Celery — UTC, локальное время СТО считается в коде.
10. **CSS/JS:** Pico.css 2.0.6 + HTMX 2.0.4 лежат в `static/vendor/` (не CDN: зарубежные CDN
    из РФ доступны нестабильно, кабинет не должен от них зависеть). Статику в проде отдаёт
    WhiteNoise.
11. **Тесты** гоняются на PostgreSQL (как в проде), `config.settings.test`: Celery eager,
    in-memory storage, ключи внешних API принудительно пустые.
12. **Локально Python 3.13**, в Docker — 3.12 (как в ТЗ); код совместим с обоими.

## Правки схемы данных (согласованы после этапа 1)

Вносятся в соответствующих этапах, когда появляются модели:

1. `Recommendation.planned_for` (date, nullable) — нужен для 7.4 («рекомендации с
   `planned_for <= today + 1`»); пересчитывается после импорта и изменений машины. *(этап 5)*
2. `Outreach.first_touch_at` (datetime, nullable) — начало окна атрибуции 9.1. *(этап 5)*
3. `Message.touch_number` (int) + `UniqueConstraint(outreach, touch_number)` для исходящих —
   защита от двойной отправки (раздел 11). *(этап 6)*
4. Лимит SMS: 2 склеенных сегмента UCS-2 = **134** кириллических символа (2 × 67), а не 140.
   Длину считаем по реальной кодировке: если текст целиком в GSM-7 — 2 × 153. *(этап 6)*
5. Уникальность клиента — условные ограничения PostgreSQL *(сделано на этапе 2)*:
   `(station, phone) WHERE phone IS NOT NULL` и
   `(station, external_id) WHERE phone IS NULL AND external_id IS NOT NULL`;
   плюс CHECK: должен быть телефон или внешний ID.

## Этап 2. Импорт

1. **Даты визитов — `DateField`** (`opened_at`, `closed_at`, `last_visit_at`): в выгрузках СТО
   время визита неинформативно, а планировщик работает в днях. Если колонка «дата закрытия» не
   задана и ЗН закрыт — `closed_at = opened_at`. У отменённых ЗН `closed_at` пуст.
2. **`ImportMappingProfile.layout`** (`flat|header`) — добавлено поле, в ТЗ формат описан, но не
   хранился. Также добавлены `ImportBatch.original_filename`, `finished_at`.
3. **Дополнительные логические поля маппинга** сверх ТЗ: «Отказы клиента» (ячейка со списком
   невыполненных работ — типично для формата «шапка ЗН»), «Сумма ЗН», «Статус ЗН», «Тип
   позиции», «Кол-во», «Цена», «Дата закрытия». Все необязательные.
4. **Идемпотентность**: ЗН ищется по `(station, external_number)`; для каждого ЗН считается
   `content_hash` нормализованных данных. Совпал — ЗН не трогаем («без изменений»), иначе
   обновляем поля, **полностью заменяем строки** и ставим `extraction_status=pending`.
   Вся запись выполняется в одной транзакции: падение воркера откатывает всё, задачу можно
   перезапустить. Задача повторно не обрабатывает уже завершённую загрузку.
5. **Сопоставление клиента**: сначала по телефону, затем по внешнему ID — но только если у
   найденного клиента нет телефона (или у строки его нет). Разные телефоны с одним внешним ID
   → разные клиенты (по ТЗ уникальность по телефону). Непустые ФИО/телефон/ID из файла
   дополняют карточку; согласия и отписка импортом не меняются.
6. **Сопоставление машины** — в пределах клиента: по VIN → по госномеру → по марке+модели
   (если ровно одна такая) → единственная машина клиента (если в строке нет данных о машине).
   Иначе создаётся новая. Смена владельца (тот же VIN у другого клиента) пока не
   отслеживается — две записи Vehicle.
7. **Нормализация**: телефоны через `phonenumbers` (регион RU, 10-значные «9…» и «8…»
   приводятся к +7), невалидные — `None` + предупреждение. Госномер: верхний регистр, без
   пробелов, латинские буквы-двойники → кириллица. Невалидный VIN отбрасывается.
   Признак выполнения: по умолчанию «выполнено»; «нет/0/отказ/не выполнено/…» → отказ.
   Если сумма ЗН не задана — сумма выполненных строк.
8. **Ошибки** пишутся с номерами строк файла и без значений ячеек (без ПДн), максимум 500.
   ЗН без даты или без телефона/ID пропускается целиком; некорректные необязательные поля
   — предупреждение, поле игнорируется.
9. **CSV**: кодировка UTF-8 (с BOM) или Windows-1251, разделитель определяется автоматически
   (`;`, `,`, tab). **XLSX**: строка заголовков — первая строка с ≥ 2 непустыми ячейками
   (пропускаем «шапку» отчёта), выбор листа на экране сопоставления.
10. **Профиль переиспользуется автоматически**, если для СТО и системы-источника есть профиль и
    все его колонки есть в новом файле; иначе — экран сопоставления с подстановкой из прошлого
    профиля и автоугадыванием по синонимам заголовков. Чекбокс «Настроить заново».
11. **Хуки для следующих этапов** — сигнал `work_orders_imported(batch, changed_work_order_ids,
    vehicle_ids)`; к нему подключатся извлечение рекомендаций (3–4) и атрибуция (7).
12. `pandas` убран из зависимостей — хватает `openpyxl` и `csv`, образ меньше.
13. **Производительность**: 10 000 строк (≈2 900 ЗН) — ~9 с, повторный импорт того же файла
    — ~2 с (локальный PostgreSQL).

## Этап 3. Справочник и правила

1. **Справочник — 89 видов работ** (`apps/catalog/seed_data.py`), засевается миграцией
   `catalog/0002` и командой `python manage.py seed_catalog` (идемпотентно: обновляет виды
   работ и пересоздаёт только *глобальные* синонимы; синонимы СТО не трогает). Интервалы —
   типовые рыночные значения, это стартовые дефолты. Регламентных (`is_regular`) — 17:
   масло ДВС, ТО, фильтры, свечи, ГРМ, приводной ремень, ОЖ, тормозная жидкость, ГУР, масла
   трансмиссии, сезонная смена шин (6 мес.), кондиционер (12 мес.).
2. **Синтаксис синонимов** (`WorkTypeAlias.kind`): `keywords` (по умолчанию) — группы через
   пробел, все должны встретиться как подстроки; `|` — альтернативы; `-слово` — запрет;
   `_` — пробел внутри альтернативы. Порядок слов не важен («Колодки пер. — замена» =
   «Замена передних колодок»). `regex` — для сложных случаев. Основы пишутся с учётом беглых
   гласных («колод», а не «колодк» — иначе не найдётся «колодок»).
3. **Выбор при нескольких совпадениях**: сначала синонимы СТО, затем глобальные; среди них —
   выше `priority`, затем самое специфичное совпадение (сумма длин найденных слов). Так
   «Замена масла АКПП» уходит в `atf_auto`, а не в `engine_oil`.
4. **Одна строка ЗН = один вид работ** (FK по ТЗ). «Замена масла и фильтра» — один тип
   `engine_oil` (масляный фильтр включён в него). Строки с несколькими разными работами
   получат один тип — ограничение, вернёмся при необходимости.
5. **Правила работают только по строкам-работам** (`kind=labor`); запчасти сопоставляются со
   справочником, но рекомендаций не создают (запчасть могли купить без установки).
   Работы открытых/отменённых ЗН сопоставляются, но рекомендаций не дают.
6. **Отказ без вида работ** (не нашёлся в справочнике) → рекомендация `needs_review`,
   `confidence=0.5`, `work_type_raw` = название строки. Отказ от работы, которая в этом же
   визите выполнена, игнорируется.
7. **Порядок обработки** — по каждой машине хронологически. Выполненная работа закрывает
   активные рекомендации того же типа с визитом источника не позже текущего (`done`,
   `closed_by_work_order`). Регламентная работа после этого создаёт новую рекомендацию.
8. **Обратная загрузка истории** (старые ЗН после новых): если есть активная рекомендация
   того же типа из более позднего визита — старый визит её не перезаписывает; если работа
   уже выполнена в более позднем визите — новая рекомендация сразу `done`.
9. **Обновление вместо дубля** (6.1): обновляются источник, срок, цитата, оценка;
   статус `scheduled` сохраняется, `needs_review` → `open`. Отклонённая менеджером
   рекомендация (`rejected`) из того же ЗН заново не создаётся. Если ЗН отредактирован и
   строки-основания больше нет — неподтверждённая рекомендация удаляется.
10. **Оценка стоимости `est_price`**: для отказа — сумма строки из сметы; иначе — средняя
    сумма этой работы (только работа, без запчастей) по СТО за 12 месяцев. Это заниженная
    оценка; прайс СТО — позже.
11. **TTL (6.4)** считается от ожидаемого срока (min(дата, дата по пробегу)), а если срока
    нет — от визита: иначе рекомендация «ремень ГРМ через 4 года» протухла бы раньше срока.
    Истечение — после каждого импорта и ежедневной задачей Celery beat.
12. Метод `Recommendation.expected_date()` реализует формулу 7.2 (без `remind_before_days`);
    поле `planned_for` добавим на этапе 5.
13. `python manage.py catalog_coverage --station N` — топ несопоставленных названий строк
    (названия работ — не ПДн). Инструмент для настройки синонимов на реальных выгрузках.
14. **Производительность**: правила работают в памяти по машинам с пакетной записью.
    10 000 строк (2 874 ЗН, 5 502 рекомендации) — импорт + правила ≈ 26 с.
15. Пока нет UI для синонимов СТО — правятся в Django admin (суперадмин).

## Этап 4. LLM-извлечение

1. **API**: Yandex AI Studio, OpenAI-совместимый endpoint `https://llm.api.cloud.yandex.net/v1`,
   SDK `openai`; ID каталога передаётся как `project` (заголовок `OpenAI-Project`), ключ —
   `Authorization: Bearer <API-key>`. Модель задаётся полным URI `gpt://<folder>/<model>/latest`
   или коротким именем — каталог подставляется сам. Формат запроса проверен тестом на
   уровне HTTP (подменный транспорт, без сети).
2. **JSON без `response_format`**: в AI Studio Chat Completions совместим частично, поэтому
   JSON берётся из текста ответа (терпим к ```-обёртке и пояснениям) и валидируется
   Pydantic. Невалидный ответ → 1 повтор → `extraction_status=failed`.
3. **Цены** в документации и новостях расходятся, поэтому живут только в
   `LLM_PRICE_PER_1K_*`. Промпт ≈ 1,5 тыс. токенов входа (справочник 89 кодов + текст).
4. **Анонимизация** (`llm/anonymize.py`): телефоны, e-mail, VIN, госномера, ФИО из карточки
   клиента (в любом падеже: основа + до 3 букв окончания), «Фамилия И.О.», «И.О. Фамилия»,
   ФИО с отчеством, 2–3 подряд слова с заглавной не в начале предложения (кроме марок и
   служебных слов). Плейсхолдеры `[ФИО]`, `[ТЕЛЕФОН]` и т.п. Тестом проверено, что ничего из
   карточки клиента не уходит в запрос.
   Общие ПДн-регулярки вынесены в `common/pii.py` (их использует и фильтр логов).
5. **Постобработка кодом** (не доверяем модели): код не из справочника → `null`;
   `source_text` не является подстрокой исходного текста → `confidence ≤ 0.3`; работы с
   кодом, выполненным в этом же визите (по правилам), выкидываются; дубли по коду — один.
6. **Статус**: `confidence ≥ 0.7` **и** найден вид работ → `open`, иначе `needs_review`
   (без вида работ рекомендацию нельзя закрыть автоматически — пусть посмотрит человек).
7. **Источник**: цитата из поля «Рекомендации» → `explicit_field`, иначе `free_text`.
8. **Сроки**: `due_km = пробег + due_km_delta`, `due_date = визит + due_months_delta`.
   Срок не указан: отказ или «срочно» → визит + 14 дней, остальное → визит + 90 дней.
9. **Правила важнее LLM**: если правила уже создали рекомендацию того же типа из этого
   визита — LLM-дубль не создаётся. Повторное извлечение заменяет прежний неподтверждённый
   LLM-вывод этого ЗН; отклонённое менеджером не воскрешается. Работа, выполненная в более
   позднем визите, сразу закрывает рекомендацию.
10. **Что не отправляем в LLM** (`skipped`): ЗН без текста (ТЗ), не закрытые ЗН и ЗН старше
    `llm_extract_max_age_days` (по умолчанию = `recommendation_ttl_days`, 540 дней) —
    при загрузке многолетней истории рекомендации из них всё равно истекли бы, а платить за
    них не нужно. Настройка точки, можно поменять.
11. **Параллельность**: сетевые вызовы — в `ThreadPoolExecutor(LLM_CONCURRENCY)`, вся запись
    в БД — в основном потоке. Задача берёт до `LLM_EXTRACT_BATCH_SIZE` ЗН и перезапускает
    себя, пока очередь не пуста. Запуск — после каждого импорта (после правил).
12. **Бюджет**: перед каждой порцией сверяем расход точки за календарный месяц с
    `LLM_MONTHLY_BUDGET_RUB`. Превышение → ЗН остаются `pending` (пауза, не ошибка),
    письмо суперадминам один раз в месяц (`LLMBudgetAlert`). Расход по СТО за месяц — в
    админке «Вызовы LLM».
13. **Ключ не задан** → извлечение не падает: ЗН остаются `pending`, в логе предупреждение;
    возобновится после настройки.
14. **`LLMCall.payload`** пишется только при `LLM_LOG_PAYLOADS=True` и содержит уже
    анонимизированный вход и ответ. Ошибки — только тип исключения/HTTP-статус.
15. **`LLM_BACKEND=fake`** — офлайн-эвристика (`llm_mock.py`: фразы текста через матчер
    справочника) для dev-демо без ключа и для `eval_extraction --model mock`. В тестах
    реальный API не вызывается никогда (`LLM_BACKEND=fake` в test-настройках).
16. **Eval**: precision/recall/F1 по наличию рекомендации (на уровне ЗН) и по
    `work_type_code` (micro по множествам кодов), токены, задержка, стоимость на ЗН,
    `--min-precision` для CI. Вход анонимизируется и выполненные работы исключаются так же,
    как в проде. Эталон: 20 синтетических примеров (`tests/golden/make_golden.py`).
    Ожидания не включают работы, выполненные в этом визите (их покрывает правило регламента).
17. **Вкладка «На проверке»**: подтвердить / исправить (вид работ, срочность, срок) /
    отклонить, HTMX без перезагрузки. Решение пишется в `review_decision_by/at` и в общий
    журнал аудита `AuditEvent` (было/стало, без ПДн) — он же пригодится на этапах 5–6.

## Этап 5. Планировщик и очередь

1. **`Recommendation.planned_for`** хранит «сырую» дату по формуле 7.2
   (`min(due_date, дата по пробегу) − remind_before_days`), не зависящую от дня расчёта.
   Дата в прошлом = «отправить в ближайший день отправки»: очередь берёт всё с
   `planned_for ≤ сегодня + 1`, а само напоминание создаётся на сегодня. Без даты и без
   пробега (`planned_for = null`) рекомендация в очередь не попадает.
   Пересчёт: после импорта, после LLM-извлечения, после решения менеджера и перед каждой
   сборкой очереди.
2. **Объединение (`merge_window_days`)**: если у машины есть хотя бы одна «созревшая»
   рекомендация, в то же напоминание добавляются все её открытые рекомендации с
   `planned_for` в пределах окна от сегодня. Только «будущие» без созревших — не повод писать.
3. **Пропуски (7.4.3)** с причиной создают запись `Outreach(status=skipped, skip_reason)` —
   видно в отчётах, почему не писали. Порядок проверок: отписка → нет согласия на сервисные
   уведомления (`consent_service=False`) → машина продана → нет визитов дольше
   `inactive_vehicle_days` → нет телефона и MAX. Рекомендации при этом остаются `open`.
   «Уже есть активное напоминание» — запись не создаётся (бессмысленный дубль).
4. **Cooldown** (новая настройка `skip_cooldown_days`, 30): после пропуска, отмены или
   «нет ответа» машина не попадает в очередь N дней — иначе пропущенное менеджером
   вернулось бы на следующий день, а авто-пропуски плодились бы ежедневно.
5. **Одно активное напоминание на машину** — гарантировано частичным уникальным индексом
   в PostgreSQL (статусы planned … booked), а не только кодом.
6. **Контрольная группа**: `sha256("outreach:<id>")` → корзина 0…9999 < `share·10000`;
   детерминированно и равномерно. Контрольные — `planned`, рекомендации `scheduled`
   (чтобы их не поставили в обычную очередь, пока идёт наблюдение). Через
   `attribution_window_days` после `planned_for` контрольное напоминание закрывается
   (`no_response`, если этап 7 не отметит визит), рекомендации освобождаются.
7. **Неактуальные напоминания**: если все рекомендации напоминания закрылись (новый визит,
   ответ «уже сделал»), ещё не отправленное напоминание отменяется (`cancelled`) — после
   импорта, при сборке очереди и при нажатии «Отправить».
8. **Ежедневная сборка**: Celery beat раз в час; для каждой точки, где локальное время
   ≥ 07:00 и сегодня ещё не было сборки (`QueueRun`), строится очередь. Так задача
   идемпотентна и догоняет пропущенный запуск, если воркер лежал в 07:00. Плюс кнопка
   «Обновить очередь» на экране «Сегодня» и команда `build_queue --station N [--date]`.
9. **«Отправить»** на этом этапе переводит напоминание в `approved` с каналом
   (MAX, если привязан, иначе SMS); саму отправку с учётом окна 10:00–20:00 делает этап 6.
   **«Позвонить»** — для сумм выше `high_value_call_threshold`: `approved` с каналом
   `manual_call` и скриптом звонка; в массовом «Отправить выбранные» такие строки не
   участвуют. «Пропустить» требует причину и возвращает рекомендации в `open`.
10. **Текст сообщения** — шаблон из 8.3 через Django templates; можно переопределить в
    `settings.message_template`. В шаблон передаётся **словарь** полей точки, а не модель
    (шаблон будет редактировать владелец СТО — не даём доступ к связанным объектам).
    Длину SMS и ссылки на бота MAX добавит этап 6.
11. **Аудит**: одобрение, звонок, пропуск и правка текста пишутся в `AuditEvent`. Свободный
    текст (причина пропуска, текст сообщения) в журнал не пишется — только длины, т.к. там
    могут быть ПДн.
12. **Длина текста**: в сводке работ — не больше двух (сначала «безопасность»), остальное —
    «и ещё N работ». Даже так шаблон 8.3 с реальными значениями занимает ~200–230 символов,
    а лимит ТЗ — 2 сегмента (134 кириллических символа). **Открытый вопрос к этапу 6**:
    укоротить шаблон / разрешить 3–4 сегмента / короткая ссылка.

## Этап 6. Сообщения

1. **Каналы: SMS + MAX, без Telegram** (решение заказчика). `Client.telegram_chat_id` →
   `Client.max_user_id`, `TelegramLink` → `MaxLink`, канал `telegram` → `max`.
2. **MAX Bot API** — по официальному клиенту `@maxhub/max-bot-api` (dev.max.ru из песочницы
   недоступен): база `https://platform-api2.max.ru` (старый `platform-api` помечен
   устаревшим), токен в `Authorization` без префикса, `POST /messages?user_id=…`
   `{"text", "attachments": [inline_keyboard]}`, кнопки `type: callback`, ответ на нажатие
   `POST /answers?callback_id=…`, вебхук `POST /subscriptions {url, update_types, secret}`,
   секрет приходит в заголовке `X-Max-Bot-Api-Secret`. События: `bot_started`
   (`user.user_id`, `payload`), `message_created` (`message.sender.user_id`,
   `message.body.{mid,text}`), `message_callback` (`callback.{callback_id,payload,user}`).
   Формат проверен тестами на уровне HTTP. **Не подтверждено**: формат deep-link с
   параметром запуска — вынесен в `MAX_LINK_TEMPLATE` (по умолчанию
   `https://max.ru/{bot}?start={payload}`), проверить на живом боте.
3. **Привязка MAX**: первое SMS содержит ссылку на бота с одноразовым токеном
   (`MaxLink`, 12 символов). `bot_started` с токеном → `client.max_user_id`; бот
   здоровается и повторяет текущее напоминание уже с кнопками (это не новое касание).
   Бот MAX может писать только тем, кто его запустил, — поэтому первое касание всегда SMS.
4. **Канал**: MAX, если клиент привязал бота, иначе SMS. Если выбран MAX, а привязки нет —
   SMS.
5. **SMS коротко** (решение заказчика): шаблон «Иван, СТО «Мотор»: по Lada Vesta пора —
   замена ремня ГРМ. Запись: <ссылка>. СТОП — отписка». Подбор варианта под лимит
   `SMS_MAX_SEGMENTS` (2): каждый шаблон пробуется с двумя работами, затем с одной и
   «и ещё N работ»; последний запасной — без перечня («пора на сервис по рекомендациям
   мастера»). Сегменты считаются честно: GSM-7 (160/153, расширенные символы за 2) или
   UCS-2 (70/67, эмодзи за 2). Если ручной текст менеджера длиннее лимита — предупреждение
   на экране. В MAX — полный текст из 8.3 и кнопки «Записаться / Уже сделал / Неактуально».
   Шаблоны можно переопределить в настройках точки (`sms_template`, `message_template`).
6. **Окно отправки**: «Отправить» ставит задачу сразу, она отправляет только внутри
   `send_window` по местному времени точки; остальное отправляет периодическая задача
   (каждые 10 минут). Ответы клиенту в переписке окном не ограничены (он сам написал).
7. **Защита от двойной отправки**: уникальность (напоминание, номер касания) в БД.
   Сообщение помечается `sending` до вызова провайдера; «зависшее» `sending` (падение
   воркера посреди отправки) **не переотправляется** — лучше не дослать, чем отправить
   дважды. Ошибка провайдера → до 3 попыток, затем напоминание отменяется с причиной.
8. **Входящие** (8.4): сначала правило СТОП (`стоп/stop/отписаться/отписка` целым
   сообщением) → отписка, отмена неотправленных напоминаний, подтверждение. Затем LLM
   (`intent_v1`, лёгкая модель, анонимизация, учёт и бюджет как у извлечения).
   `confidence < 0.7`, ошибка LLM, бюджет или `other` → «Диалоги», без автоответа.
   `preferred_time_text` принимается, только если это цитата из ответа клиента —
   модель не может «придумать» время. ИИ никогда не подтверждает время сам.
   Добавлен интент `not_relevant` (кнопка «Неактуально» → рекомендации `declined`).
   «Продал машину» → `vehicle.is_sold`. Вопрос о цене без оценки → менеджеру.
9. **Кнопки MAX** обрабатываются без LLM; кнопка принимается, только если напоминание
   принадлежит этому же пользователю MAX. Повторная доставка вебхука отсекается
   уникальностью (`channel`, `provider_message_id`) для входящих.
10. **Входящие SMS**: общий вебхук `/messaging/sms/inbound/` `{"phone","text","id"}` с
    секретом `X-Vozvrat-Secret` — адаптер конкретного провайдера появится вместе с
    провайдером. Один телефон может быть у клиентов разных точек → берём того, кому писали
    последним.
11. **Повторное касание** (8.5): при сборке очереди «отправлено, ответа нет
    `second_touch_after_days`» → снова «ждёт подтверждения» (свой шаблон: «напоминает»);
    после `max_touches` → `no_response`, рекомендации освобождаются.
12. **Звонки**: «Позвонить» → блок «Звонки» на «Сегодня» с исходами «Записан / Не
    дозвонились / Отказался»; звонок — касание (`Message`, канал `manual_call`).
    «Не дозвонились» идёт по общей логике повторного касания.
13. **SMS-провайдер не выбран**: есть интерфейс бэкенда и `ConsoleBackend`; реальный
    провайдер — отдельный класс в `messaging/backends/`, когда будет выбран.
14. **Экран «Диалоги»**: клиенты с ответами, требующими внимания, переписка, ответ
    менеджера (аудит — только длина текста), «Отметить обработанным».
15. Ссылка-приглашение (`MaxLink`) создаётся лениво — при первом показе текста SMS
    (превью на «Сегодня» или отправка) и переиспользуется, пока клиент её не открыл.

## Этап 7. Атрибуция и отчёт

1. **Атрибуция** запускается после каждого импорта (после правил и планировщика). Окно:
   `[дата первого касания по местному времени точки, + attribution_window_days]`
   включительно; для контрольной группы — от `planned_for`. Засчитывается самый ранний
   не отменённый ЗН машины в окне; один ЗН — одному напоминанию (при пересечении окон —
   более позднему). `attributed_amount = total_amount` ЗН.
2. **Кандидаты**: `sent | replied | booked` по ТЗ **плюс `no_response`** — клиент может
   приехать, не ответив; после двух касаний без ответа окно ещё не закончилось. Для
   контроля — `planned` и `no_response` (контрольные закрываются планировщиком по окну).
3. **Исправлена ошибка этапа 5**: «неактуальные» напоминания (все рекомендации закрыты)
   отменялись и в контрольной группе — визит, закрывший рекомендацию, терялся до
   атрибуции, и эффект рассылки завышался. Контрольные напоминания больше не отменяются.
4. **Когорта отчёта** — напоминания с `planned_for` в периоде; «Найдено рекомендаций» —
   по дате визита-источника в периоде. «Ответили» — есть входящее сообщение;
   «Заявки» — напоминания с заявкой; «Приехали» и выручка — по атрибуции.
5. **Сравнение с контролем**: доля приехавших среди отправленных и среди контрольных,
   разница в п.п., оценка доп. выручки по формуле ТЗ, где «средний чек приехавших» —
   средняя выручка приехавших **из рассылки**. Дополнительно: 95% доверительный интервал
   разницы (нормальное приближение) и пометки «мало данных» (< 30 в группе), «не значимо»,
   «окно атрибуции ещё открыто у N напоминаний» — чтобы владелец не делал выводов по шуму.
6. **«Деньги на столе»** — текущее состояние (не зависит от периода): активные
   рекомендации (`open`, `needs_review`, `scheduled`) и сумма `est_price` по видам работ.
7. **Доступ**: «Результаты» — только Owner и Superadmin (раздел 2); Manager получает 403.
   Фильтр по точке — только точки, доступные пользователю.
8. **CSV**: агрегаты (без ПДн), разделитель `;`, UTF-8 с BOM — открывается в Excel.

## Доводка (после этапа 7)

1. **`delete_client_data --client-id N [--yes]`** (раздел 11): без `--yes` показывает, что
   будет удалено; с `--yes` удаляет клиента, машины, ЗН и строки, рекомендации,
   напоминания, сообщения, заявки, ссылки MAX. **Файлы выгрузок**, где были строки клиента,
   тоже удаляются (файл общий для многих клиентов, но это лишь копия выгрузки СТО;
   статистика загрузки остаётся). В журнале аудита — только id и количества. Из отчётов
   за прошлые периоды исчезают и напоминания этого клиента — осознанно.
2. **Срок хранения выгрузок** `IMPORT_FILE_RETENTION_DAYS` (30): файлы с ПДн удаляются
   ежедневной задачей через N дней после обработки; записи о загрузках и статистика
   остаются.
3. **Экран «Клиенты»**: поиск по ФИО, телефону (любой формат, по последним 10 цифрам),
   госномеру, VIN, ID в системе СТО. Карточка: контакты, отписка (с отменой
   неотправленных напоминаний) и восстановление подписки только с отметкой «клиент сам
   попросил», заметки, машины с оценкой пробега и отметкой «продана», рекомендации,
   напоминания, история ЗН. Полный телефон в кабинете виден (менеджер звонит клиентам);
   маскируется он только в Django admin. Все действия — в аудит, без текста заметок.
4. **Экран «Настройки»** (только владелец и суперадмин, текущая точка): данные точки
   (часовой пояс — из списка российских, подпись ≤ 30 символов, чтобы SMS помещалось),
   правила 7.3 (окно отправки только в пределах 08:00–22:00, контрольная группа 0–50%),
   шаблоны SMS/MAX с проверкой синтаксиса и обязательным «СТОП», превью на примере и счёт
   сегментов, пользователи: владелец создаёт **только администраторов** (Manager) своей
   организации, отключает/включает их; себя, других владельцев и чужих — нельзя.
   В аудит пишутся изменённые поля (для правил — было/стало).
5. Переформулировка текста через LLM (`llm_compose_enabled`, 8.3) не сделана — флаг
   необязательный и по умолчанию выключен.

## Дизайн и тёмная тема

1. **Дизайн-система поверх Pico.css**: токены `--v-*` (фон, поверхности, текст, бирюзовый
   основной цвет, янтарный акцент, статусы success/warning/danger/info) для светлой и
   тёмной темы; переменные Pico привязаны к токенам. Шрифт Inter Variable (кириллица +
   латиница, OFL) и иконки Lucide (ISC) лежат в `static/vendor` — без внешних CDN.
2. **Тема**: «Авто» (по настройке ОС) → «Светлая» → «Тёмная», переключатель в меню и на
   странице входа; выбор хранится в браузере (`localStorage`) и применяется
   встроенным скриптом до первой отрисовки — без мигания.
3. **Каркас**: боковое меню с иконками и подсветкой раздела; на экранах уже 1024 px меню
   выезжает по кнопке (CSS-only, без JS); проверено отсутствие горизонтальной прокрутки
   на 390 px.
4. Исправлено: на «Сегодня» не выводилось число SMS-сегментов (в шаблон строки не
   передавались канал и подсчёт). Отрицательная «дополнительная выручка» и разница
   теперь красные, положительные — зелёные.

## Демо-данные (`load_demo`)

1. Демо идёт **через настоящий конвейер** (импорт двух выгрузок, правила, извлечение,
   очередь, отправка, ответы, атрибуция) — экраны показывают реальное поведение системы,
   а не подставленные цифры. Даты — относительно сегодняшнего дня (кампания 25 дней назад,
   визиты после неё, очередь на сегодня).
2. Внешний мир **принудительно офлайн** независимо от `.env`: LLM — эвристика, отправка —
   `ConsoleBackend`, Celery-задачи не ставятся (подмены действуют на всё время транзакции,
   включая `on_commit`). Все люди, телефоны (+7900…), VIN и госномера выдуманы.
3. Отдельная организация «Демо-сеть автосервисов», пользователи `demo` (владелец) и
   `manager`; повторный запуск пересоздаёт, `--remove` удаляет. При `DEBUG=False` —
   только с `--force`.
4. На «Результатах» добавлены быстрые периоды: «Этот месяц» (по умолчанию, как в ТЗ),
   «Прошлый месяц», «30 дней», «90 дней».
